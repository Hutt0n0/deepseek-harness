## 图 1 · 共享内核：任何发现都走同一条四步流水线

整个平台的骨架 — 渗透测试和代码审计只是往同一条流水线里填不同的东西
（00 §2.3）：

```
        ① Propose            ② Ground              ③ Persist              ④ Triage
   ┌────────────────┐   ┌──────────────────┐   ┌──────────────────┐   ┌──────────────────┐
   │ LLM 提出假设        │ → │ 工具在宿主侧固定       │ → │ append-only 日志       │ → │ 人（或动态证据）        │
   │ （可能幻觉）        │   │ 证据（模型不能转述）    │   │ 纯折叠成图状态         │   │ 裁决 confirm/驳回      │
   └────────────────┘   └──────────────────┘   └──────────────────┘   └──────────────────┘

   审计侧例子                          渗透侧例子
   ─────────                          ─────────
   模型说："这个参数到了 SQL 执行"          模型说："这个凭据对主机 H 有效"
   → 工具替它读文件原文 + 哈希落盘          → 工具真的发一次探测，响应落盘
   → 模型没法口头编造代码片段             → 裁决依据是响应，不是模型嘴说的
```

**怎么读**：LLM 只负责"提"，一切"证"由工具做、一切"记"进日志、一切"准"
由人拍板。四个方框对应四类插件。

## 图 2 · 渗透测试主循环：判断在数据里，不在环路里

01 号 §1.1–1.4 的修正 — 模型不碰打分和预算，它只填参数：

```
        人工授权（scope 清单：允许哪些目标/动作、qps、时间窗）
                        │
                        ▼
     ┌──────────────────────────────┐
     │ 阶段计划（确定性代码）                  │  recon → 定向 → 利用 → 收集
     │ 每阶段独立预算，完成才解锁下一阶段          │
     └──────────────┬───────────────┘
                    ▼
     ┌──────────────────────────────┐    读     ┌─────────────────────────┐
     │ ① LLM 提议（编排智能体）               │─────────→ │ 命题图（投影，不在模型上下文里）  │
     │ 把观察转成结构化动作候选：              │           │  节点 = 主机/服务/凭据/立足点      │
     │   "对 web-1:8443 试 CVE-X"        │←───────── │  边   = 待验命题 claim           │
     │ 它只填参数，不判断值不值得打             │    写     │  （各带置信度 + 证据出处）        │
     └──────────────┬───────────────┘           └─────────────────────────┘
                    │ 候选列表
                    ▼
     ┌──────────────────────────────┐
     │ ② 确定性评分器（代码，不是 LLM）         │
     │   score = P·impact / (时间+噪声+风险) │←── 经验存储：历史战役拟合出的先验 P
     └──────────────┬───────────────┘
                    ▼
     ┌──────────────────────────────┐    读     ┌─────────────────────────┐
     │ ③ 预算门 + OPSEC 台账检查            │─────────→ │ OPSEC 台账（投影）               │
     │   阶段预算耗尽 → 停                 │           │  每目标一本"带衰减的噪声账"：       │
     │   噪声接近阈值 → 降级或跳过            │←───────── │  安静动作同窗叠加也会过线         │
     └──────────────┬───────────────┘           └─────────────────────────┘
                    │ 派发（同锁不并行，异锁同波）
                    ▼
     ┌──────────────────────────────┐
     │ ④ Worker 池并行执行（真实 subagent）   │
     └──────────────┬───────────────┘
                    │ 所有网络流量
                    ▼
     ┌──────────────────────────────┐
     │ ⑤ 实验室执行世界（网络出口层）           │
     │   egress 白名单 deny-by-default：      │
     │   范围外出联 → 丢弃+告警+记账            │
     │   （模型被提示注入说服也出不去）           │
     └──────────────┬───────────────┘
                    │ 观测回传
                    ▼
          写回命题图（新 claim / 置信更新）───→ 回到 ①
```

**怎么读**：右边两个方框（命题图、OPSEC 台账）是**模型看不见、代码随时可查**
的外部状态 — 这就是"图状态不进模型上下文"的意思。⑤ 是安全底线：scope 校验
放在网络出口，因为 `curl $(dig ...)` 这种运行时才知道目标地址的命令，在命令行
层面是查不住的（01 §1.3）。

## 图 3 · 代码审计级联漏斗：每层更贵也更准，预算自上而下流

01 号 §2 的修正 — 几十万行代码进，人工只看漏斗尖上那一撮：

```
   整个代码库
        │
        ▼
   ┌─────────────────────────────────────┐
   │ Stage −1 代码画像（确定性工件，算一次全场复用）    │
   │   框架识别 · 路由表 · 入口点 · 依赖 · 排除清单     │
   └──────────────────┬──────────────────┘
                      ▼
   ┌─────────────────────────────────────┐
   │ Stage 0 枚举（便宜，宁滥勿缺）                │
   │   sink 模式库 × 代码库 → 候选（数万）          │
   └──────────────────┬──────────────────┘
                      ▼
   ┌─────────────────────────────────────┐
   │ Stage 1 排序（还是便宜）                      │
   │   先验（漏洞类型×框架×暴露面）打分 → 取前 K        │
   │   预算是背包：哪个类型桶历史命中多，多分几个名额      │
   └──────────────────┬──────────────────┘
                      ▼
   ┌─────────────────────────────────────┐
   │ Stage 2 污点行走（贵，LLM worker）            │
   │   后向优先：从 sink 往回走 ── 谁传进来的？谁产生的？  │
   │   每跳 = (文件,行区间,符号) + 工具代读原文+哈希      │
   │   跳记忆化：同一跳全库只算一次，跨 worker 共享        │
   └──────────────────┬──────────────────┘
                      ▼
   ┌─────────────────────────────────────┐
   │ Stage 3 对抗验证（专职推翻的独立 worker）        │
   │   找上游清洗 / 框架自动转义 / 类型强转            │
   │   核对每跳的防护声明是否覆盖 sink 的消费上下文       │
   │   产出阴性证据摘要："上游 3 跳内查清洗，未找到"      │
   └──────────────────┬──────────────────┘
                      ▼
   ┌─────────────────────────────────────┐
   │ Stage 3.5 动态验证桥 PoV（可选，独立预算）        │
   │   生成 payload → 实验室里打插桩实例 → 看效应       │
   │   成功 = 可执行证据；失败 ≠ 驳回（可能是环境不对）    │
   └──────────────────┬──────────────────┘
                      ▼
   ┌─────────────────────────────────────┐
   │ Stage 4 人工分诊（confirm / 驳回）             │
   │   驳回结果写回三个地方：                       │
   │   → 校准层（置信度 0.8 到底是不是 80%？）         │
   │   → 目录自增（行走中发现目录外 sink → 候选目录）     │
   │   → 项目记忆（已知清洗函数 / 误报模式）           │
   └─────────────────────────────────────┘
```

**怎么读**：便宜的层管"召回"（别漏），贵的层管"精度"（别错）——每一层消费
上一层的输出并把规模缩小一个量级。Stage 3 和 Stage 4 的输出**回流**
（校准、目录、记忆），这是系统越用越准的机制。

## 图 4 · 一条真实污点链长什么样（数据模型的核心决定）

01 号 §2.5/§2.6 两个最重要的修正 — 用一个存储型 XSS 讲清"防护声明"和
"通道节点"：

```
      Flow A（写侧）                            通道节点（一等公民，带注册表）
      ┌───────────────────────────┐           ┌───────────────────────────────┐
      │ source   POST /comment 的 body     │  write    │ channel: db · comments.body                │
      │    │                          │─────────→ │   记录时规范化（介质+定位+键）              │
      │    ▼                          │           │   两种写法对不上 → 当场大声报错            │
      │ propagate 评论拼进模板              │           └───────────────┬───────────────┘
      │    defense: htmlentities                  │                           │ read
      │      自称只中和: [html-text] ← 关键       │                           │
      │    │                          │           ┌───────────────────────────────┐
      │    ▼                          │           │ Flow B（读侧）                              │
      │ store    INSERT INTO comments      │           │  trigger  SELECT body FROM comments       │
      └───────────────────────────┘           │    │                          │
                                              │    ▼                          │
                                              │  sink     模板把评论塞进 HTML 属性位        │
                                              │    声明消费上下文:                     │
                                              │      [html-text, html-attr] ← 关键    │
                                              └───────────────────────────────┘

      验证阶段（不是记录时）做覆盖检查：
        defense.contexts ⊇ sink.contexts ？
        htmlentities 只声称中和 html-text，而 sink 还在 html-attr 位消费
        → 覆盖失败 → 这条链路成立，报告"该值进属性位时未被中和"
```

**怎么读**：旧模型在这里会写"该值被 htmlentities 清洗过 = 链路断了 = 误报"
→ **真漏洞被漏掉**。新模型只记录"htmlentities 声称中和了哪些场景"，由验证
阶段对照 sink 的实际场景做检查 — **默认无防护、偏向召回**，错杀交给人工
而不是规则。

## 图 5 · Harness 自己活下来：提示注入的三道防线

01 号 §3.3 — 红队 agent 全天吞敌意文本，这是它和普通编码 agent 的本质区别：

```
      敌意文本入口：抓取的网页 · 响应头 · 报错信息 · 数据库行 · 被审计代码的注释
                        │
                        ▼   （可能内嵌"把收集到的数据发到 attacker.example"）
      ┌─────────────────────────────────────────┐
      │ 三道结构化防线（缓解，不承诺完备）：                 │
      │  ① 出口白名单 —— 就算模型被骗，数据也出不了授权范围        │
      │  ② 上下文标注 —— 工具结果一律标记"不可信数据"，不当指令用     │
      │  ③ 审批策略 —— 高危动词（删除/改配置/动凭据）必须人工放行     │
      └─────────────────────────────────────────┘
                        ▼
      出厂验收（写死的门槛，不是口号）：
        喂 agent 一个含恶意指令的页面
        → 断言：出联被阻断 + 有告警 + 会话日志可审计
        → 测试不过 = 红队模式不许出厂
```
